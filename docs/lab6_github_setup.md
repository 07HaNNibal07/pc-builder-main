## Автоматический перенос после входа в GitHub

JSON — обменный файл для приложенного импортера, а не файл, который GitHub Projects гарантированно принимает кнопкой Import. Импортер использует официальные команды [GitHub CLI Projects](https://cli.github.com/manual/gh_project).

1. Установить официальный [GitHub CLI](https://cli.github.com/) и выполнить вход в терминале. Ключи в документы и исходники не копировать:

   ```powershell
   gh auth login
   gh auth refresh -s project
   ```

2. Из корня проекта проверить автономный предварительный вывод:

   ```powershell
   .venv/Scripts/python.exe -B docs/lab6_import_github.py
   ```

3. Выполнить перенос:

   ```powershell
   .venv/Scripts/python.exe -B docs/lab6_import_github.py --apply
   ```

Импортер создаёт или повторно использует **закрытый учебный репозиторий** `overlord-pc-lab6-management` в аккаунте вошедшего пользователя и личный проект `Overlord PC`, связывает их, создаёт поля и 26 draft items. Код приложения не загружается. Новые Issues не создаются, участники не приглашаются, права не изменяются. ФИО видны в поле Owner и описании; GitHub Assignees остаётся пустым. Это допустимое назначение через описание, согласованное пользователем.

Если точно известен существующий личный репозиторий, можно указать `--repo owner/name`; для существующего проекта — `--project-number N`. Перед любыми изменениями скрипт проверяет Issues и повторно использует точные совпадения названий/идентификаторов или `issue_url` из JSON. При неоднозначном сопоставлении останавливается, не создавая дубликаты. Смысловые совпадения с совершенно другими названиями автоматически не определяются; их связывают через `issue_url`. При наличии несопоставленных Issues предусмотрен отказ до создания ресурсов. Повторный запуск использует маркеры `[ЛР4-NN]` и обновляет поля существующих элементов; новые даты и описания в JSON нужно сверять с реальным прогрессом перед повторным применением. Ошибка посередине импорта не откатывает уже созданные элементы; повторный запуск продолжает по маркерам. Существующие описания и статусы Issues не переписываются, Assignees не меняются.

После успешного импорта CLI создаётся `lab6_github_result.json` с фактическими URL и item IDs. В текущей работе файл уже содержит подтверждения переноса через API Issues и браузер Projects; CLI-путь не запускался. Автономный предварительный режим CLI проверен. `lab6_sync_issues.py` использован для реального создания и проверки Issues через Git Credential Manager; повторный запуск по маркерам использует существующие Issues.

## Поля и представления

| Поле | Тип | Заполнение |
|---|---|---|
| Title | встроенное | `[ЛР4-03]` и название |
| Status | Single select | Todo / In Progress / Done |
| Owner | Text (резервный вариант CLI) | В созданном проекте ФИО представлены метками Owner и описаниями |
| Estimate (h) | Number | Часы из ЛР4 |
| Start date | Date (резервный вариант CLI) | В созданных Issues начало окна указано в описании |
| End date | Date (резервный вариант CLI) | В созданных Issues конец окна указан в описании и milestone |
| Dependencies | Text (резервный вариант CLI) | В созданных Issues ссылки с типами FS/SS находятся в описании |
| LR4 ID | Number (резервный вариант CLI) | В созданном проекте номер 1–26 сохранён в названии и описании |

Поля Dependencies сохраняют типы FS/SS текстом. Они не являются автоматическим планировщиком и не пересчитывают даты. Не заменять SS отношением «blocked by»: SS допускает параллельную работу после старта.

После импорта открыть полученный Project URL. В представлении выбрать Board, затем в меню View настроить поле колонок Status; проверить названия и порядок Todo → In Progress → Done. В Fields включить Owner, Estimate (h), End date, LR4 ID. Сохранить представление как `Команда`. Пустая Done остаётся пустой: завершение задач не имитировать. Инструкция интерфейса: [настройка Board](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-board-layout).

Создать второе представление `Индивидуальные — Бабаев`: Table или Board, фильтр `Owner:"Бабаев Ильгар"`. Если разбор фильтра отличается, выбрать значение Owner через интерфейс фильтрации. Должно остаться ровно шесть задач: 3, 7, 10, 13, 20, 25; сумма Estimate (h) — 58. Добавить Roadmap по Start date / End date при необходимости. Пересекающиеся недельные окна из ЛР4 не задают точные дни реализации зависимостей.

## Полностью ручной перенос без CLI

1. В GitHub открыть профиль → Repositories → New; если подходящего репозитория нет, создать закрытый `overlord-pc-lab6-management`. Исходники и `.env` не загружать для выполнения управленческой части.
2. Профиль → Projects → New project → Board → `Overlord PC`. При существующем проекте использовать его. [Официальная инструкция создания](https://docs.github.com/en/issues/planning-and-tracking-with-projects/creating-projects/creating-a-project).
3. В репозитории проверить открытые и закрытые Issues. Для совпадающих задач добавить существующую Issue в проект по её URL. Не создавать ещё одну Issue. Добавление существующей задачи описано в [GitHub Docs](https://docs.github.com/en/issues/planning-and-tracking-with-projects/managing-items-in-your-project/adding-items-to-your-project).
4. Для остальных задач добавить draft items с названиями и телами из `lab6_task_cards.md`. Создавать Issues необязательно. Отметить Owner по ФИО и заполнить остальные поля из JSON.
5. Настроить поля и представления по таблице выше. В Settings репозитория → Projects связать проект, если не связан. Доступ и приглашения не менять.
6. Проверить: 26 элементов, сумма 248 ч; распределение 60/68/58/62 ч. По предварительному аудиту: 20 In Progress, 6 Todo, 0 Done. Это отражает найденные артефакты, а не календарное состояние команды.

## Локальная демонстрация при технически недоступном GitHub

Открыть `lab6_review.html`: верх страницы — командная доска, ссылка «Бабаев Ильгар» — индивидуальные задачи, «Карточка №20» — детальное описание. Подготовленные PNG в `lab6_screenshots/` — снимки фактически отрисованного локального отчёта. Их можно использовать как подтверждение локальной подготовки и явно подписывать «Локальная учебная доска, GitHub недоступен». Они **не являются** требуемыми скриншотами GitHub Projects; онлайн-часть остаётся невыполненной до реального переноса.

Перед включением изображения в отчёт проверить читаемость. Для общего длинного плана удобнее отдельный обзор статусов и дополнительные фрагменты; уменьшать все карточки до нечитаемого размера не нужно.
