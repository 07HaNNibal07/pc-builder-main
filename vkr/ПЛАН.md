**Берём** (это общие правила, они же в действующих ГОСТ):
- состав: титульный лист, задание, аннотация (реферат), содержание, введение, главы, заключение,
  список использованных источников, приложения;

- разделы с новой страницы (введение, заключение, список, приложения — тоже); номера «2», «2.5», «2.5.3»
  без точки в конце; единственный подраздел в разделе не выделяется;

  слева; нумерация сквозная; ссылка в тексте обязательна («в соответствии с рисунком 2», «см. таблицу 1»);
- формулы — отдельной строкой по центру, номер «(1)» справа, пояснения с «где» без двоеточия;
- ссылки на источники — «[12]», в список — только то, на что есть ссылка;
- приложения «Приложение А», «Приложение Б» (без Ё, З, Й, О, Ч, Ь, Ы, Ъ), каждое с новой страницы;
- маркированные списки — только дефис «—»; нумерованные — «1)»;
- доклад на защите 10–15 минут: актуальность, место среди аналогов, постановка задачи с допущениями,
  новизна и достоверность, использование результатов.

**Не берём без подтверждения руководителя** (это требования другой кафедры или отменённые стандарты):
- рамка со штампом по ГОСТ 2.104-68 и поля 2 / 0,5 / 0,5 / 0,5 см — это ЕСКД для конструкторских

## 3. Структура записки

По таблице 4 заявки — четыре главы. В скобках — откуда брать материал.

**Реферат (аннотация).** Объём, число рисунков, таблиц, источников, приложений; ключевые слова; цель,
методы, результаты, применение.

**Введение.** Актуальность (таблица цен Palit RTX 5070 из заявки), объект и предмет, цель, задачи
(8 задач заявки), новизна, практическая значимость, структура работы.

**1 Анализ предметной области**
- 1.1 Процесс выбора конфигурации ПК и его трудоёмкость (40 операций сравнения)
- 1.2 Обзор существующих решений: конфигураторы магазинов (DNS, Ситилинк, Регард), агрегаторы цен
  (e-Katalog, Яндекс Маркет), PCPartPicker; таблица сравнения; вывод — чего нет ни у кого
- 1.3 Источники данных: пять площадок, способы доступа, ограничения (лимиты WB, капча Ali, заголовки,
  `recon/RECON.md`, архив памяти) — таблица 2 заявки с фактическими цифрами
- 1.4 Постановка задачи и требования к системе (функциональные, нефункциональные)
- 1.5 Выбор методов и средств реализации (Python, FastAPI, PostgreSQL, CDP, Docker; three.js для 3D)

**2 Проектирование системы**
- 2.1 Архитектура: четыре подсистемы, сбор отделён от обслуживания запросов (схема)
- 2.2 Модель данных: модель — предложение — ценовой срез — сеанс — сопоставление (ER-диаграмма, `db/schema.sql`)
- 2.3 Алгоритм установления тождества позиций: артикул → имя эталона DNS → признаки (формула сходства)
- 2.4 Правила технической совместимости (перечень предикатов с порогами)
- 2.5 Метод подбора конфигурации: отбор по Парето, полезность, варианты «экономная / оптимальная /
  с запасом», доплата, улучшение сборки
- 2.6 Модель оценки FPS: «узкое место», мягкий минимум, баллы TechPowerUp, поправки (формулы)
- 2.7 Проектирование интерфейса (макеты экранов, 3D-модель)

**3 Программная реализация**
- 3.1 Структура проекта и модули
- 3.2 Подсистема сбора: адаптеры площадок, браузерный сборщик, планировщик, журнал сеансов
- 3.3 Подсистема нормализации: разбор наименований, карточки товаров, каталог
- 3.4 Подсистема подбора и HTTP API (`/docs`)
- 3.5 Веб-интерфейс и 3D-модель сборки
- 3.6 Тестирование (модульные тесты, сценарии), развёртывание (Docker, сервер)

**4 Экспериментальное исследование**
- 4.1 Качество сопоставления: точность, полнота, F-мера на размеченной выборке ≥ 200 позиций
- 4.2 Экономический эффект: сборка системы vs эквивалентная сборка на одной площадке, по сценариям
- 4.3 Сокращение трудоёмкости: время подбора вручную и с системой
- 4.4 Достоверность модели FPS: прогноз vs замеры (`docs/FPS_VALIDATION.md`)
- 4.5 Выводы

**Заключение.** Результаты по каждой задаче, степень выполнения задания, направления развития.

**Список использованных источников.** ГОСТы, документация (FastAPI, PostgreSQL, CDP), обзоры TechPowerUp,
статьи по entity resolution / record linkage, по многокритериальному выбору.

**Приложения.** А — техническое задание (если нужно); Б — схема БД; В — листинги ключевых модулей;
Г — экранные формы; Д — руководство пользователя / развёртывания.

## 4. Заявка и то, что сделано

| Пункт заявки | Сейчас | Что делать |
|---|---|---|
| Подбор под бюджет и назначение | есть: игры (3 разрешения), работа, офис | «видеомонтаж / графика» = «работа» — так и описать |
| Приоритеты методом анализа иерархий (попарные сравнения) | нет: полезность = FPS / многопоток | **доделать** (МАИ на 3 критерия) или заменить формулировку |
| Критерий «потенциал модернизации» | нет | доделать (сокет, DDR5, запас БП) вместе с МАИ |
| Несколько недоминируемых альтернатив | есть: Парето по CPU × GPU, 3 варианта | описать |
| Объяснение выбора по каждой позиции | есть | описать |
| Фиксация комплектующих, подбор вокруг них | частично: замена детали с проверкой | доделать «подобрать остальное» или переформулировать |
| Модернизация имеющейся сборки | есть (+ «не про FPS») | описать |
| Проверка совместимости с объяснением | есть, с числами | описать |
| Сравнение цен по площадкам, итог | есть: значки площадок со ссылками | добавить «сколько на одной площадке» — нужно и для 4.2 |
| Динамика цены | есть: график в «Сборке» | копить историю до защиты |
| Отклонение цены от средней за период | нет | небольшая доработка |
| Контроль цены с уведомлением | нет | в «направления развития» |
| Каталог с фильтрами, сравнение моделей | нет (поиск по названию в замене) | решить с руководителем |
| Панель оператора, мониторинг источников | нет интерфейса: `schedule --plan`, журнал в БД | небольшая страница или описать как CLI |
| Ручная сверка сопоставлений | в БД есть (`matches.method = 'manual'`), интерфейса нет | нужна для разметки в 4.1 — сделать простую |
| Правила совместимости в конфигурации | нет: в коде (`advisor.check`), таблица `compatibility_rules` не используется | перенести или переформулировать |
| Сходство: Левенштейн + Жаккар | фактически Жаккар по токенам + совпадение признаков, порог 0,7, зазор 0,1 | описать как есть |
| Планировщик APScheduler | `collector/schedule.py` + Планировщик Windows | описать как есть |
| Три эксперимента | не проведены | **главное до защиты** |
| История цен ≥ 6 месяцев | 4 дня | регулярный сбор |

Сверх заявки (в записку как достоинства): 3D-модель сборки с проверкой габаритов, модель FPS с
проверкой на реальном ПК, улучшения «не про FPS», развёртывание на сервере.
